# 既存アプリ診断モード(実装が進んでいる・申請済みのアプリに渡された時)

このフォーマットを、すでに実装が進んでいる、または申請(審査)まで済んだアプリに渡された場合は、
段階0(ダイス・設計書の再設計)から始めず、次の手順で進める。

## 方針
- **レビューと安全の基準は常に100%**。ダイスには依存しない。
- ダイス(`randomdice.md`)は、オーナーが「設計を作り直したい」と言った時だけ振る。
- オーナーの「変更不可」と既存の良い資産(デザイン・コード)は尊重する。むやみに作り替えない。
- 問題が解決するまで対応を続ける。途中で終わらせない。

## 手順
### 1. 取り込みと現状把握(質問は最小限)
1. `setup.sh` でフォーマットを取り込む(既存ファイルは上書きしない)。
2. コード、`docs/`、App Store Connect の状況(分かる範囲)、過去の審査指摘を読み、現状を把握する。
3. 状態を判定する: ①実装中 ②実装完了・未申請 ③申請済み(審査待ち) ④リジェクト後 ⑤公開済み(アップデート)。

### 2. チェック(診断)
状態に応じて、該当する段階を実行する。重い指示は必要なものだけ。
| 状態 | 実行するもの |
|---|---|
| ①実装中 | `1_planning.md`(同型・薄さ)、`2_development.md`、`2b_edge_cases.md` |
| ②実装完了・未申請 | `2_development.md`、`2b_edge_cases.md`、`3_submission.md`、`codex_review.md`(Codex用) |
| ③申請済み | `3_submission.md` の観点で、申告と実装の食い違い(プライバシー、年齢制限、課金)を確認 |
| ④リジェクト後 | 指摘文を読み、該当ガイドラインを特定。`1_planning.md` で重複・テンプレート性を診断し、返信か修正かを判断 |
| ⑤公開済み | 変更範囲に応じた `2_development.md`、`3_submission.md`、更新時の再申告項目 |

診断結果は、「重大 / 推奨 / 提案」に分け、根拠(ファイルと行、公式資料)を添える。

### 3. オーナーへの質問(診断の後に、まとめて)
診断結果を短く見せたうえで、次を丁寧に質問する。選択肢つき、番号で答えられる形にする。
1. 最優先の目的はどれか(リジェクトを解消 / 品質を上げる / 売れる方向に直す / 申請を通す / その他)
2. 守りたいもの(変更不可の機能・デザイン・名前)
3. 変えてよい範囲(小さな修正まで / 画面の再設計まで / 設計から作り直し)
4. 期限や制約(いつまでに、使える時間、予算)
5. 診断で見つけた問題のうち、先に直すもの

「おまかせ」と言われたら、重大 → 推奨の順で進める。

### 4. 対応(返答に従って、解決まで)
1. 合意した範囲で、修正・追加・文面作成を行う。大きな変更(コンセプト、名前、収益化、主要機能)は、実装前に確認する。
2. 修正ごとにビルド・テストを実行し、`docs/devlog.md` に記録する。
3. 区切りで再チェック(該当する段階)を行い、重大な問題が残っていないことを確認する。
4. 審査対応が必要なら、返信文・申請キット(`appstore/`)を作る。個人情報は書かず、本人が手入力する。
5. 問題が解決するまで、2〜4を繰り返す。解決したら、解決の根拠(確認した内容)を報告する。
6. 申請まで済んだら、`ExperiencePoints.md` への追記候補をオーナーに見せる。

## 報告の形
- 診断: 状態、重大/推奨/提案の一覧(短く)
- 質問: 番号つき
- 対応後: 直したもの、確認結果、残りの問題
