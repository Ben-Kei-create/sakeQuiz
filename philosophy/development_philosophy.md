# 開発思想(オーナーらしさ)

> 機能は削る。体験は削らない。
> 小さなアプリを、完成度の高い作品として届ける。

判断に迷ったら、この思想に戻る。AI は、設計書・実装・レビューのすべてでこれを基準にする。

## 6つの柱
| | | 意味 |
|---|---|---|
| 01 | Simple | ひとつの明確な目的 |
| 02 | Original | 模倣しない独自性 |
| 03 | Beautiful | 細部まで一貫したデザイン |
| 04 | Intuitive | 説明なしで使える操作(できれば片手) |
| 05 | Efficient | AI活用による省力化 |
| 06 | Sustainable | 低コストで継続できる事業 |

## 核になる考え方
- **「シンプル」と「高品質」は矛盾しない。** 情報量は減らし、残した要素一つひとつの品質を上げる。簡素でも安っぽくしない(余白・配置・文字・色を徹底する)。
- **機能の少なさそのものを価値にする。** 便利そうな機能を足し続けない。独自性のために機能を増やさない。一つのルールで個性を出す。
- **高度な機能ほど操作は簡単に。** 主要な行為を一つに集約する。複雑さはユーザーに見せない。
- **操作に対する画面の変化で達成感を出す。** 数値だけの成長にしない。
- **世界観を統一する。** アイコンからアプリ内部まで、デザインの思想を一致させる。
- **既存の良い資産を尊重する。** 過去の良いデザイン・コードをむやみに作り替えない。新しいUIが常に優れているとは限らない。

## 過去作から取り入れたい発想
| 作品 | 取り入れる思想 |
|---|---|
| ドパリカ! | 正解で上昇、誤答で下降。操作に画面の変化を結びつけ、復習も自然に組み込む |
| PageMint | 画像をドラッグ&ドロップするだけ。裏の複雑さを見せず、主要な行為を一つに集約 |
| C-Log | 復活時も必要以上にモダン化せず、元の個性を守りつつ品質と使いやすさを改善 |
| ヘイドラム | 用途を一つに徹底。機能を増やさず、少なさを価値にする |
| Karrage / 架空アイドル / Toiret / Zayping | 奇抜な題材、1日1回の制限、画面全体で完結する操作、強いシンボル |

## 審査との緊張(必ず意識する)
架空アイドルのように「題材を変えれば別アプリになる仕組み」を再利用する発想は、開発効率の面で優れている。
一方で、wineryQuiz が 4.3(a)(b)・4.2.6 でリジェクトされた原因は、まさに「同型で題材だけ違う」ことだった。
- ゲームの**仕組み(ルール)**を再利用するのは良い。ただし、**体験・見た目・名前・ストアでの見え方**は、アプリごとに明確に変える。
- 姉妹アプリは、構図や質感を揃えつつ、**題材で区別できる**ことに加えて、**単体で独立した価値**があること。
- 迷ったら `review_prompts/1_planning.md` と `1b_growth.md` で、同型に見えないかを確認する。

## 改善したいこと(自分への注意)
1. **画面デザインを確定する前に実装を進めすぎない。** 先にアイコン、ホーム画面、代表的な操作画面を揃える。ただし画像と実機の操作感は違うので、早い段階で実機プロトタイプも確認する。
2. **機能追加と独自性を混同しない。**
3. **使い捨て開発を減らす。** ボタンやカード、データ保存、課金、設定画面、アセット管理、ストア申請文面は、テンプレート化する(全アプリの見た目を同じにする意味ではない)。
4. **実装完了とリリース完了を分ける。** リリース完了 = ストア文面、スクリーンショット、課金表示、プライバシー設定、実機テストまで含む。
5. **収益化と運用コストは企画段階で決める。** 広告・買い切り・サブスクを製品特性で選び、体験を遮る広告は避ける。サーバーや AI API の継続費用も先に見積もる。
