# App Store Connect 申請キット作成指示書 v2.2
初回リリース・アップデート共通 / iOS・macOS対応 / 手動コピペ最適化

【最重要】これは AI 作業者に渡す共通指示書。依頼が「指示書のリライト」なら申請処理は実行せず編集のみ行う。

## 使い方と実行条件
1. `appstore/app_input.md` にアプリ固有情報(非個人情報)を入れる。
2. `review_prompts/` の段階1・2・3の審査チェックを全て完了させる。
3. **段階3まで全て通過してから**、この指示書で申請用のコピペリスト `appstore/kit.md` を作る。通過前に完成版を作らない。途中で求められたら、準備版と明記し、不足と完了条件を示す。
4. `kit.md` には個人情報を一切書かない(下記)。そのためコミットしてよい。
5. 個人情報の欄は、本人が App Store Connect で直接手入力する。

## 個人情報の扱い(最優先)
- **キットに書かない(本人が手入力)**: 姓名、メールアドレス、住所、審査用アカウントのパスワード、鍵・トークン、著作権表記に含まれる氏名。
- **電話番号**は、実番号を書かず `+81 XXXXXXXXXX` の形で書く。X の部分は本人が手入力する。
- 該当する欄は、【扱い】を「本人が手入力」とし、貼り付けブロックは作らない(電話番号だけ、上記の `+81 XXXXXXXXXX` を示す)。
- 著作権欄は、書式だけ示す(例: `© 年 氏名. All rights reserved.`)。氏名は本人が入れる。
- 個人情報をリポジトリ、コミット、PR、公開ページ、チャットに書かない。
- 個人情報以外(アプリ名、説明文、キーワード、公開URL、審査メモ、回答の選択)は、`kit.md` に実値で書いてよい。
- `scripts/pre-commit`(`setup.sh` が入れる)が、メールアドレスや電話番号らしい文字列、`private/` のファイルを含むコミットを自動で中止する。

## 入力欄の運用
1. AI は必ず `appstore/app_input.md` を最初に読み、過去のバージョンや他アプリの情報より、今回の明示値を優先する。コード・既存登録情報との矛盾は報告し、勝手に上書きしない。
2. 「自動確認」の欄は可能な限り AI が調べ、調べられない時だけ不足として報告する。未登録と不明を混同しない。
3. 初回は App ID・アプリレコード作成から案内し、更新は既存レコードを前提に変更点と必須の再申告だけを案内する。
4. 広告の設定やアプリ名を他プロジェクトへ引き継がない。広告ID(AdMob のアプリID・広告ユニットID)は App Store Connect の入力欄にないので、キットには含めない。
5. 完成キットは、App Store Connect を上から順に埋められるよう、画面名 → セクション → 項目名 → コピペ用の値／選択肢の順で出す。

## 0. 目的と運用原則
対象アプリの実装、Xcode設定、提出素材、Apple公式要件、公開ページ、App Store Connect で確認できる登録情報を調査し、ユーザー自身が管理画面を上から順に操作・コピペできる「申請キット」を作る。
対象は初回リリース、初回登録途中、既存バージョンのアップデート、メタデータ修正、iOS と macOS の両方。別アプリの情報を流用しない。
App Store Connect と Apple Developer の操作は本人が行う。AI は勝手にブラウザ操作、登録、提出、課金契約、公開を行わない。各画面の「入力値」「選択回答」「手動操作」「確認のみ」を厳密に区別する。
日付基準は作業時点の日本時間。Apple公式の最新の日本語画面表記を優先し、英語表示なら英語名を併記する。画面上にない欄を捏造しない。

## 1. 申請モードとビルド状態の判定
- A: 初回・App ID未登録
- B: 初回・App ID登録済み / アプリレコード未作成
- C: 初回・レコード作成済み / ビルド未アップロード
- D: 初回・ビルドアップロード済み / 審査準備中
- E: 既存アプリのアップデート
- F: メタデータ・プライバシー等のみの変更
- G: その他 / 判定不能(証拠と不足を示す)

判定根拠、対象プラットフォーム、App ID、Bundle ID、Apple ID、CFBundleShortVersionString、CFBundleVersion、アップロード済みビルドの有無、現ステータスを冒頭に記載する。最初の5行以内で、「今回必要なビルド形式」「現在ある/不足している」「初回/更新」を知らせる。申請に必要なのは Xcode プロジェクトそのものではなく、署名済みビルドであることを説明する。
更新時は既存設定を引き継ぎ、変更が必要な項目だけ再入力させる。登録済みの Bundle ID や SKU を変更できると誤案内しない。

## 2. 対象アプリの特定
- アプリ名、リポジトリとブランチ、Bundle ID、App ID、SKU、Apple ID(それぞれ確認状況を区別)
- 現行/申請バージョン、ビルド番号
- プラットフォーム、対応OS・端末・言語、カテゴリ、価格、配信地域、リリース方法
- 既存のレコード、過去の審査指摘、公開情報
- 広告・分析・課金・ログイン・外部通信・ユーザーデータ・権限
- 商標・素材・ライセンス・暗号化・トラッキング・子ども向け要件

アプリ固有の情報は他アプリから補完しない。提案は「提案」として、本人が確定した情報と区別する。
ソースがローカルに無い場合は、既存のチェックアウトを探し、なければ実在する URL で clone する手順を示す。URL 不明なら実行可能なコマンドとして出さない。

## 3. 共通オーナー情報
個人情報(姓名、メール、電話、著作権表記の氏名)は、キットに書かず、本人が手入力する。
サイト運営者、サイトのリポジトリ、問い合わせ先の表記などは、不明なら本人に確認する(推測しない)。
公開URLの規則は `appstore/common.md`。
管理画面の実情報や本人の新しい指示と食い違う場合は、勝手に確定せず差分を報告する。
- トレーダー(Trader)としての申告は、本人の方針を確認して従う。法的・地域別の必要情報は、実際の登録主体に基づき確認する。
- 配信方針は `app_input.md` に従う。国・地域別の法的要件、契約、年齢制限、輸出規制で調整が必要か確認する。
- 広告方針: 導入状況と種類は必ずコードと AdMob 設定で確認する。
- プライバシー方針: 初回は必要最低限。将来、興味関心データを扱うなら、機能導入・同意・開示の変更が必要。導入前に収集済みと申告しない。

## 4. 操作権限
- 承認なし: コード・SDK・権利・Apple公式仕様の調査、原稿作成、素材案とローカル画像生成、Web ページの作業ブランチ作成、ローカル検証、PR準備
- 明示承認が必要: アプリコード/Xcode設定/PrivacyInfo.xcprivacy の変更、権限・課金・広告・ATT の動作変更、管理画面での変更、ビルドアップロード、本番サイト公開、PRマージ、契約・税務・銀行口座の変更、審査送信、リリース
- 禁止: 依頼に含まれないアプリ削除、配信停止、アクセス権変更、秘密鍵・パスワード・トークンの出力

## 5. 作業フロー
1. モード・アプリ特定
2. App ID / アプリレコードの有無確認
3. コード・SDK・データ収集・権限・署名の調査
4. 公式仕様の照合
5. 説明文、申告回答、画像等の準備
6. 公開ページの準備
7. Xcode 検証・Archive・アップロードの要否確認
8. 入力キットの作成
9. 未完了・承認事項の明示
10. 本人による管理画面入力・審査送信

未完了項目があっても、貼れる確定済みの欄は先に出す。未確定欄は「入力保留」とし、理由と完了条件を示す。完成版と準備版を区別し、完成版と呼ぶのは必須要件が揃った時だけ。

## 6. 出力形式(画面順 + 1フィールド1ブロック)
出力先: `appstore/kit.md`(個人情報を含まない)。
タイトル: `[アプリ名] App Store Connect申請キット｜[初回/更新]｜v[バージョン]`
冒頭に「今回の入力順」「対象プラットフォーム」「Xcodeビルド形式」「申請可否」「本人操作の残件」を短く示す。
各入力欄に、次の書式を繰り返す。

```
【画面】アプリ → [対象アプリ] → iOS App → [バージョン]
【セクション】[Apple画面の正式表記]
【入力欄・タグ】[実際の欄名]
【扱い】今回入力/前回値を維持/設定済み・確認のみ/利用時のみ/対象外/入力保留
【操作】テキスト貼り付け/プルダウン選択/ラジオ選択/チェックを付ける/チェックを外す/スイッチON/OFF/ファイルをアップロード/表示確認
【根拠】プロジェクト実装/App Store Connect現設定/Apple公式資料/本人決定事項
【文字制限】上限と原稿の実測文字数
【貼り付け内容】
(この欄に貼る文字列のみをコードブロックで)
```

- 貼り付け用ブロックには、説明・見出し・注釈・引用記号・文字数・未確定のプレースホルダーを入れない。個人情報の欄は、貼り付けブロックを作らず「本人が手入力」と書く(電話番号だけ `+81 XXXXXXXXXX`)。URL、アプリ名、説明文、キーワードは別々のブロックにする。
- 選択式は回答ラベルを明記する。存在しない欄は対象外と理由を示す。ファイルは用途、保存場所、ピクセル寸法、形式、実在確認を明示する。
- 同じ値が複数画面に必要なら、画面ごとに再掲する(「前述と同じ」は禁止)。
- 言語ごとに独立して記載する。実画面の見出しと順序を優先する。
- 更新時は各欄に「変更/据え置き/新設/対象外」の区別を入れ、前回の説明との整合を示す。

## 7. 初回専用: 登録の順序
- Apple Developer → Certificates, Identifiers & Profiles → Identifiers: App ID の有無を確認。未登録なら登録手順を示す。明示的 App ID、Bundle ID、必要な Capabilities を、実装に照らして示す。Xcode の署名設定と一致させる。
- App Store Connect → アプリ → + → 新規アプリ: プラットフォーム/名前/プライマリ言語/Bundle ID/SKU/ユーザアクセスを、ラベルごとに入力・選択方法付きで示す。
- 初回の注意: Apple ID はレコード作成後に表示される。更新時に既存の SKU や Bundle ID を再入力させない。

## 8. 画面別の出力範囲
実在しない機能は無理に設けず、適用対象だけを出す。

### 8-1. バージョン情報
バージョン番号、言語、プレビューとスクリーンショット(デバイス枠ごと)、プロモーション用テキスト、説明、キーワード、サポートURL、マーケティングURL、著作権、新機能(What's New)、関連機能の欄、提出ビルド。
初回は「新機能」が必須か現行画面で確認する。更新時は差分に基づく完成原稿を作る。機能や修正内容を架空で足さない。

### 8-2. App Reviewに関する情報
サインインの要否、審査用アカウントの要否、名/姓/メール(本人が手入力。値は書かない)、電話番号(`+81 XXXXXXXXXX` の形を示し、X は本人が入力)、審査メモ、再現手順、特別なハードウェア/地域/権限/広告/課金復元、添付ファイル。審査用認証情報の秘密はチャットに出さず、安全に手入力させる。ログイン不要なら不要と明記する。

### 8-3. バージョンのリリース
手動/自動/指定日時。日時指定ならタイムゾーンを明記。段階的リリースの設定が出る場合は分けて記載。

### 8-4. アプリ情報
アプリ名、サブタイトル、プライマリ言語、Bundle ID、SKU、Apple ID、カテゴリ、コンテンツ配信権、使用許諾契約、年齢制限の設問全文と回答、年齢適合性URL、地域別の対応、地域固有の許認可。編集できない表示値は「確認のみ」とする。

### 8-5. アプリのプライバシー
プライバシーポリシーURL(必須)、ユーザーのプライバシー選択URL(該当時)、データ収集の有無、該当するデータタイプ、目的、ユーザーへの関連付け、トラッキングの有無。SDK と収集経路を照合し、広告ID・IDFA・ATT・端末内保存を混同しない。データカテゴリは実画面の小分類まで列挙し、未選択のカテゴリも明示する。変更時は現行の申告との差分も示す。

### 8-6. アクセシビリティ
VoiceOver、音声コントロール、文字拡大、ダークインターフェイス、色以外での区別、十分なコントラスト、視差効果の軽減、字幕、音声ガイドなど、表示される項目を実機検証に基づき回答する。動作確認なしの適合宣言は禁止。

### 8-7. 価格および配信状況
価格、基準の国・地域、配信国・地域、税金カテゴリ、予約注文、公開方法、Apple シリコン搭載 Mac や Apple Vision Pro での配信可否、教育機関向け割引。最低OS要件は Xcode 設定と照合する。

### 8-8. アプリ内購入/サブスクリプション
実装済みの場合のみ、製品ごとに参照名、商品ID、ローカライズ、表示名、説明、期間/種類、価格、配信地域、税区分、審査メモと画像、ファミリー共有、更新/復元関連を整理する。初回の課金商品をバージョンに添付する要件を確認する。未実装なら「対象外」とし、架空の商品を作らない。

### 8-9. 規制・コンプライアンス
輸出コンプライアンス/暗号化、トレーダーステータス、地域別の事業者情報・登録・許可・表示、コンテンツ配信権、第三者の権利、医療機器関連の申告。回答は実装と登録の実態から個別に判断する。暗号化は「HTTPS を使っているから必ず免除」と決めつけない。

### 8-10. その他
TestFlight、成長とマーケティング、Game Center などは、利用時に限って整理する。今回の提出に不要なら別枠で対象外とする。評価とレビュー、アナリティクス、審査履歴などは入力欄ではなく確認画面として区別する。

## 9. 記述・画像の品質ルール
- Apple公式の最新の文字制限を確認し、テキストは省略せず欄ごとに完成形で出す。説明文には未実装の機能を含めない。キーワードの区切りや重複を確認する。
- スクリーンショットの手順と確認項目は `appstore/screenshots.md`(Xcode のシミュレータで撮影。捏造しない。テスト広告を写さない)に従う。
- スクリーンショットは実際に動くアプリ画面を撮影する。構成は5〜6枚を推奨するが、必須枚数は Apple公式で確認する。推奨構成: ①特徴・メイン画面 ②主要機能 ③操作方法 ④差別化機能 ⑤設定や履歴 ⑥その他実在の特徴。アプリにない画面や機能を捏造しない。プレビュー動画は任意。
- 提出用スクリーンショットは、Apple公式の現行のデバイス枠・ピクセルサイズ・形式に適合させる。固定のピクセル例を現行必須と断定しない。macOS は別途確認する。提出用とWeb縮小版は分ける。
- 画像パスは存在を確認したものに限る。アイコン未作成なら、Xcode の実際の要件(正方形1024px等)を確認して作成する。提案画像と適用済み画像を混同しない。

## 10. 公開Webページの作成・更新
**申請と同時に(遅くとも申請の前に)公開済みにする。申請完了後に作らない。**広告の都合(AdMob、app-ads.txt)と、App Store Connect のURL入力のため。雛形は `web/`。
サイトのリポジトリは本人に確認、公開URLの規則は `appstore/common.md`、スラッグは `app_input.md` に従う。既存の有効なチェックアウトを優先し、無ければ空のディレクトリに clone する。
初回に作るもの: アプリのトップ、サポート、プライバシー、images の各ページ/ディレクトリ。更新時は既存ページを優先して修正し、URL を変えない(必要なら承認を得る)。
- 既存ページの構成・トーン・共通CSSを踏襲する。トップ(ロゴ・紹介・画面・遊び方・アプリ情報表・サポート/プライバシーへのリンク)、サポート(問い合わせと、実機能の FAQ 約3件)、プライバシー(SDK・収集・送信・保持・削除・同意・外部サービス・子ども関連)。
- プライバシーポリシーと App Store Connect の申告を必ず一致させる。ユーザーデータや保持期間を推測しない。制定日は実際の制定・改訂日を使う。
- 問い合わせ先は、スパム対策の表記で載せる(表記は本人に確認)。メールアドレスをそのまま公開しない。
- Web画像は幅約480pxに縮小し、1画像約100KB以下、全体で約1MB以内を目標にする。img には width, height, alt, loading=lazy を付ける。高解像度の提出用ファイルは Web に入れない。
- 変更許可範囲: 対象アプリのフォルダ、アプリ一覧のカード、sitemap。既存の他ページや他アプリは変更禁止。独立した新しい CSS は作らない。
- 作業ブランチ作成 → 作成・検証 → PRとプレビュー確認 → 本人へ提示 → 明示承認後にマージ → 本番の HTTP 200 と内容確認。プレビュー URL や予定 URL を公開済みと記載しない。

## 11. AdMob・プライバシー・SDK監査
- バナー/インタースティシャル/リワードを、アプリ別に実装確認する。広告ユニットIDの使い回しは禁止。アプリIDと広告ユニットIDを混同しない。
- Google Mobile Ads SDK のバージョン、初期化、同意管理、IDFA、ATT、SKAdNetwork、プライバシーマニフェスト、app-ads.txt、EU・英国・スイス等の同意要件を確認する。
- 初回は最小限の実装・最小限のデータ収集にする。将来の興味関心利用は予定に留め、未実装なら今回の収集として申告しない。実装するアップデート時に SDK、ポリシー、説明と同意を更新する。
- UserDefaults 等の端末内保存だけで「外部収集あり」と判断しない。逆に、ログインが無くても SDK 経由の収集はあり得る。事実に基づいて判断する。

## 12. Xcode / Archive / 提出ビルド
検証順: プロジェクト・Target → Bundle ID → Team・署名 → Deployment Target → Version/Build → Capabilities → Info.plist・権限の用途説明 → PrivacyInfo.xcprivacy → SDK → 実機動作 → Archive → Validate → Distribute App / アップロード → 処理完了・ビルド選択。
各工程を「完了/要対応/対象外/検証不能」に分類する。コマンドや操作は、実在のプロジェクトを確認してから示す。バージョンの値とビルドを一致させ、前回のビルド番号との整合を確認する。Archive・アップロードは承認後に行う。TestFlight 専用配布と App Store 審査用の違いも、必要に応じて説明する。

## 13. 進捗時の出力と最終品質ゲート
準備中でも、次の順に回答する。
1. 今すぐ入力できる項目(画面順、コピペブロック)
2. 選択・チェック・アップロードが必要な項目(画面順)
3. 設定済みで確認のみの項目
4. 未完了項目(画面名、理由、完了条件、担当者)
5. 作成済みファイル/公開済みURL/PR/検証結果
6. 本人が操作する次の一手

禁止: 「情報不足でキットを一切出さない」「確認していないのに完成と呼ぶ」「原稿の代わりに抽象的な説明を置く」。
完成と呼ぶ条件: 公開ページが本番で公開済み、必須入力と回答の根拠・整合、App ID とレコード、コード・権限・広告・プライバシー、実機テスト、署名・ビルド、公開Webページ、画像、権利、審査メモ、価格・地域・規制が確認済みであること。審査送信や公開承認は「予定された最終操作」として別扱い。
更新では「前回値を維持できるもの」と「改めて申告・提出するもの」を分け、変更に伴う年齢制限・トラッキング・課金・権限・スクリーンショット・審査メモ・サイトの修正を再検証する。

## 14. 終了時のまとめ
- モード、App ID、Bundle ID、SKU、Apple ID、現在/申請バージョン・ビルド
- 画面別の入力/選択/アップロード/確認のみ一覧
- 公開済みのトップ/サポート/プライバシーURLとアクセス結果
- 提出素材のファイル名・サイズ・形式・保存場所・確認結果
- 実装とストア説明、SDK とプライバシー、契約・地域・権利との整合
- 完了/未完了/承認待ちの区別
- 使用した公式資料名、URL、確認日
- 次にクリックする実際の画面・ボタン
- **個人情報がコミットに含まれていないことの確認結果**
