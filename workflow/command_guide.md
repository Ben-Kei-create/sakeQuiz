# コマンド・スキル使い分けガイド(品質を上げつつ、トークンを節約する)

目的: **適切なタイミングで、適切な道具を、必要な強さだけ**使う。
重いものを常時使わず、効果が大きい場面にだけ投入する。
コマンドやスキルは、Claude Code のバージョンや環境で変わる。迷ったら `/help` で確認し、無いものは使わない。

## 1. 節約の基本(いつも守る)
| やること | 理由 |
|---|---|
| 無関係な作業に移る前に `/clear` | 古い会話が毎回の入力に乗り続けるのを止める。最大の節約 |
| 長くなったら `/compact`(残したい点を添える) | 会話を要約して軽くする。例: `/compact 設計書の決定事項と未解決のバグを残す` |
| `/context` や `/cost` で消費を見る | 何が重いかを把握する(コマンドが無い環境では省略) |
| `CLAUDE.md` は短く保つ | 毎セッション全文が読み込まれる。詳細は別ファイルに置き、必要な時だけ読ませる |
| 広い検索は Explore(サブエージェント)に任せる | 検索結果の大量の出力を、本編の会話に入れない |
| 指示は「今回の変更範囲」だけにする | 設計書(正本)は参照させ、毎回貼り直さない |
| 同じ質問・同じ調査を繰り返さない | 結果は `docs/` に残して、次回はそれを読む |

## 2. モデルと強さの使い分け
| 作業 | 目安 |
|---|---|
| 企画、設計の判断、難しいバグ | 高性能モデル、考える量を多めに |
| 通常の実装、テスト、文書作成 | 標準モデル、標準の強さ |
| 機械的な置換、整形、一覧の作成 | 軽量モデル、考える量を少なく |
| 独立レビュー | Codex(別系統の目で見る。Claude Code とは別の枠で動く) |

`/model` で切り替える。最初から最強にせず、詰まった時に上げる。

## 3. 段階ごとのおすすめ
### 段階0〜1b(企画)
- **プランモード**(Shift+Tab で切り替え)で、実装前に計画だけ出させる。やり直しが安い。
- `./scripts/roll_dice.sh` でダイス → 余りがあれば調査 → 設計書の書き直し。調査は重いので、**会話を分けて**(`/clear` してから)行い、結果を `docs/research_memo.md` に残す。
- 企画が終わったら `/clear`。次の会話は、設計書と採用プランだけを読ませて始める。

### 実装(段階2)
- 画面デザインが確定してから実装に入る。変更範囲を小さく区切り、1回の指示=1つの機能にする。
- 実装後は、**その場でビルド・テストを実行**させる(失敗を後で見つけるほど高くつく)。
- `/simplify`(変更したコードの整理): 機能が一区切りついた時に1回。毎回は不要。
- `/code-review low` か `medium`: 区切りごとの確認。`max` は費用が大きいので、**オーナーが明示した時だけ**。
- `/security-review`: 提出前と、通信・権限・SDK を足した時だけ。
- `/run`: 実際にアプリを起動して動作を見たい時。
- コンテキストが重くなったら `/compact`、機能が変わったら `/clear`。

### 想定外の洗い出し(段階2b)
- `review_prompts/2b_edge_cases.md` は、機能が出揃ってから**1回**。毎回の実装で回さない。
- 見つかったバグは `docs/edge_cases.md` に書いてから直す(会話が消えても残る)。

### Codex レビュー
- 区切り(機能完成、提出前)で `review_prompts/codex_review.md` を渡す。
- Codex の指摘は、重大/推奨/提案に分かれて返る。Claude Code には「重大」と「推奨」だけを渡して直させる。

### 提出前(段階3)
- 審査チェック(段階3)→ 申請キット(`appstore/`)の順。
- 環境にあれば、`engineering:deploy-checklist`(提出前の確認)、`design:accessibility-review`(アクセシビリティ)、`design:design-critique`(UIの批評)も、**この段階で1回ずつ**。
- ストア用の文面は、`design:ux-copy` が使えるなら補助にする。

## 4. 使うタイミングの早見表
| 場面 | 使うもの | 頻度 |
|---|---|---|
| 新しい作業を始める | `/clear` | 毎回 |
| 長い作業の途中 | `/compact 〜` | 重いと感じたら |
| 設計・企画 | プランモード | 企画のたび |
| 広い範囲の調査 | Explore サブエージェント | 必要な時 |
| 一区切りの実装 | `/simplify` | 区切りごとに1回 |
| 変更の確認 | `/code-review low/medium` | 区切りごと |
| 権限・通信・SDKを足した | `/security-review` | その時と提出前 |
| 動作確認 | `/run` | 画面を変えた時 |
| 定期的に見たい(CI、ビルドなど) | `/loop`(間隔は長めに) | 必要な時のみ |
| 権限の確認ダイアログが多い | `/fewer-permission-prompts` | 一度設定すれば十分 |
| 新しいリポジトリを始める | `/init` | 初回のみ(ただし `setup.sh` が入れる `CLAUDE.md` を優先) |

## 5. やらないこと(節約の落とし穴)
- 毎回 `max` のレビューを回す、長大な設計書を毎回丸ごと貼る。
- 1つの会話で、企画・実装・申請準備を全部やる(後半ほど高く、精度も落ちる)。
- `/loop` を短い間隔で回し続ける。
- 同じ内容を `CLAUDE.md`、設計書、指示の3か所に重複して書く。
- 動かしてもいないのに「テスト済み」と書く。

## 6. このガイドの育て方
- 消費が大きかった場面、効果が大きかった道具を、`docs/devlog.md` に書き、ここに反映する。
- 新しいコマンド・スキルが増えたら、段階の表に追記する。
